## 🛠️ Step 1: Route Questions with a Question Classifier

A **Question Classifier** asks the LLM to put the user's question into one of the classes you define. Each class gets its own output handle, so each type of question can follow its own path.

1. Hover the right edge of **User Input**, click **+**, and add a **Question Classifier**. Its input variable is already <code>sys.query</code>.
2. Select **gpt-35-turbo-16k**. Click the settings icon next to the model and set **Temperature** to <code>0</code>. Routing should be predictable, not creative.
3. Add classes until there are six, and type one name into each class's text box, in this order:

| Class | Name | Example question |
| --- | --- | --- |
| 1 | <code>specific_issue</code> | What is REST-266 about? |
| 2 | <code>list_issues</code> | Summarize REST-266 and REST-265 |
| 3 | <code>general_project</code> | What is this project about? |
| 4 | <code>test_related</code> | What should we test for backward compatibility? |
| 5 | <code>test_generation</code> | Generate test cases for REST-266 |
| 6 | <code>unrelated_or_invalid</code> | Write me a poem about the sea |

<Shot src={require('../static/img/dify/1.16.1/ex4/question-classifier.png').default} alt="Question Classifier panel with the six classes specific_issue to unrelated_or_invalid" caption="The six classes" width="420px" />

4. Class names alone are ambiguous. For example, is "Generate tests for REST-266" about a specific issue, or is it test generation? Open **Advanced Setting** at the bottom of the panel and paste this into **Instruction**:

<Copy title="Question Classifier → Advanced Setting → Instruction">{`You classify questions sent to a software testing assistant for the Atlassian REST Jira project.
Choose exactly ONE category:

- specific_issue: asks about one Jira issue that it names by key or number. Examples: "What does REST-266 fix?", "Who is assigned to issue 259?"
- list_issues: mentions two or more Jira issue keys and asks to summarize, compare or relate them. Example: "Summarize REST-266 and REST-265"
- general_project: asks about the project as a whole (scope, modules, features, contributors), about a group of issues, or which issue matches a description, without naming a key. Examples: "What is this project about?", "Which issues relate to Jackson?", "Which issue reports that CORS preflight requests are not supported?"
- test_related: asks about test strategy, risk, regression or coverage, without asking to write test cases. Example: "What should we test for backward compatibility?"
- test_generation: asks to write, generate or create test cases or Gherkin scenarios, with or without issue keys. Examples: "Generate test cases for REST-266", "Create test scenarios for a password reset feature"
- unrelated_or_invalid: not about this project, its Jira issues, its documentation or testing. Examples: "Write me a poem", "Why is the sky blue?"

If the user asks to write or generate tests, choose test_generation even when the question contains issue keys.`}</Copy>

## 🛠️ Step 2: Branch `specific_issue`: Exact-Key Retrieval

In Exercise 3, a question about REST-266 searched the whole knowledge base by meaning. Similar issues could outrank REST-266, and a key that doesn't exist still returned *something*. This branch pulls the key out of the question and retrieves **only** the document whose <code>issue_key</code> metadata matches.

<div style={{ background: '#f8fafc', border: '1px solid #cbd5e1', borderRadius: '8px', padding: '0.6em 1.2em', margin: '1em 0', fontFamily: 'monospace' }}>
  specific_issue → Issue Key Extractor → Has Key?<br />
  &nbsp;&nbsp;IF → KR - Single Issue → Issue Found?<br />
  &nbsp;&nbsp;&nbsp;&nbsp;IF → LLM - Specific Issue → Answer - Specific Issue<br />
  &nbsp;&nbsp;&nbsp;&nbsp;ELSE → Answer - Issue Not Found<br />
  &nbsp;&nbsp;ELSE → KR - General Project (the Step 4 branch)
</div>

### 2.1 Parameter Extractor: Issue Key Extractor

1. From the classifier's <code>specific_issue</code> handle, add a **Parameter Extractor** and rename it **Issue Key Extractor**. Select **gpt-35-turbo-16k** with **Temperature** <code>0</code>. The input variable is <code>User Input / query</code>.
2. Under **Extract Parameters**, click **+** and add:
   - **Name:** <code>issue_key</code>
   - **Type:** String
   - **Required:** off. Some questions look like single-issue questions but name no key; the next step handles them
   - **Description:** <code>The Jira issue key the user asks about, for example REST-266.</code>
3. Paste this into **Instruction**. The normalization line lets "issue 266" or "rest266" find REST-266:

<Copy title="Issue Key Extractor → Instruction">{`Extract the one Jira issue key the user is asking about.
A Jira issue key is an uppercase project prefix, a hyphen and a number, for example REST-266.
Normalize other spellings to that format. This project's prefix is REST, so "rest 266", "REST266", "issue 266" and "ticket 266" all become REST-266.
Return only the key.`}</Copy>

<Shot src={require('../static/img/dify/1.16.1/ex4/issue-key-extractor.png').default} alt="Issue Key Extractor with the issue_key parameter and the instruction highlighted" caption="The issue_key parameter and its instruction" width="420px" />

### 2.1b Cheaper alternative: extract the key with code

Your LLM extractor works. But look at what it does: it finds a pattern like `REST-266` in a sentence. Every question pays for an LLM call to do that, and a few lines of Python can do the same job. Here are the two measured side by side on the same questions:

| Extractor | Tokens per question | Time | "What is REST-266 about?" | "What does issue 266 fix?" |
| --- | --- | --- | --- | --- |
| Parameter Extractor (LLM) | ~550 | 1.0-1.7 s | REST-266 | REST-266 |
| Code node (Python) | 0 | ~0.1 s | REST-266 | REST-266 |

<div style={{ background: '#e0f2fe', border: '2px solid #38bdf8', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0' }}>
  <b>Rule of thumb:</b> if you can describe the answer as a pattern, use code. It's free, instant, and gives the same output every time. Keep the LLM for things only language understanding can do, such as "the ticket about Jackson leniency", where there is no key to match.
</div>

To swap the LLM for code:

1. Add a **Code** node between the Question Classifier's <code>specific_issue</code> handle and **Has Key?**, and rename it **Extract Keys (Code)**. Keep **Python3**.
2. Replace the default code with:

<Copy title="Extract Keys (Code) → Code (Python3)" language="python">{"import re\n\n# Jira projects in the knowledge base. The first one is used for bare\n# numbers such as \"issue 266\". Add more prefixes if you ingest other projects.\nPROJECTS = [\"REST\"]\n\n# A known prefix, an optional hyphen or space, and a number:\n# REST-266, rest 266, REST266\nPROJECT_KEY = re.compile(r\"\\b(\" + \"|\".join(PROJECTS) + r\")[\\s-]?(\\d+)\\b\", re.IGNORECASE)\n# A bare number after a word that means \"issue\": issue 266, ticket #266\nBARE_NUMBER = re.compile(r\"\\b(?:issue|ticket|bug)\\s*#?\\s*(\\d+)\\b\", re.IGNORECASE)\n\n\ndef main(query: str) -> dict:\n    found = []  # (position in the question, normalized key)\n    for match in PROJECT_KEY.finditer(query):\n        found.append((match.start(), match.group(1).upper() + \"-\" + match.group(2)))\n    for match in BARE_NUMBER.finditer(query):\n        found.append((match.start(), PROJECTS[0] + \"-\" + match.group(1)))\n\n    issue_keys = []\n    for _, key in sorted(found):\n        if key not in issue_keys:\n            issue_keys.append(key)\n\n    return {\n        \"issue_key\": issue_keys[0] if issue_keys else \"\",\n        \"issue_keys\": issue_keys,\n    }"}</Copy>

3. Now make the node's variables match the code. Dify passes each **input variable** to <code>main()</code> by name, and reads back the returned keys by **output variable** name, so the names must match exactly:

| In the node | Default | Change it to |
| --- | --- | --- |
| Input Variables | <code>arg1</code>, <code>arg2</code> | <code>query</code> → **User Input / query** (delete <code>arg2</code>) |
| Output Variables | <code>result</code> (String) | <code>issue_key</code> (**String**) and <code>issue_keys</code> (**Array[String]**); delete <code>result</code> |

<Shot src={require('../static/img/dify/1.16.1/ex4/extract-keys-code.png').default} alt="Extract Keys (Code) node: input query from User Input, outputs issue_key String and issue_keys Array[String]" caption="The same outputs as the LLM extractor, without an LLM" width="420px" />

4. Rewire the branch, and check each item yourself. Dify's **Checklist** (the orange badge next to **Preview**) catches only one of these mistakes:
   - Point the condition in **Has Key?**, the filter condition in **KR - Single Issue** and the variable in **Answer - Issue Not Found** at **Extract Keys (Code) / issue_key**. If you delete **Issue Key Extractor** first, all three keep pointing at a node that no longer exists. The Checklist flags the Answer node ("Invalid variable"), but **not** the filter condition. The filter then silently matches nothing.
   - Delete **Issue Key Extractor**.
   - The classifier's <code>specific_issue</code> handle connects **only** to **Extract Keys (Code)**, and <code>list_issues</code> still connects to **Issue Keys Extractor** (plural: the Step 3 node, not the one you just deleted). A class connected to two nodes is valid wiring, so nothing flags it. Dify simply runs both branches.
5. Rerun the Step 2 checks. Open the node's **Last Run** tab to see exactly what it extracted.

<div style={{ background: '#fef2f2', border: '2px solid #ef4444', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0' }}>
  <b>Something wrong after the swap?</b> Expand <b>Workflow Process</b> above the answer and compare it with these symptoms:
  <ul style={{ marginBottom: 0 }}>
    <li><b>Code node fails with</b> <code>TypeError: main() got an unexpected keyword argument 'arg1'</code>: the input variable is still <code>arg1</code>. Rename it to <code>query</code>.</li>
    <li><b>Code node fails with an error about its outputs:</b> the Output Variables don't match the keys the code returns. Use <code>issue_key</code> (String) and <code>issue_keys</code> (Array[String]).</li>
    <li><b>All nodes are green, but the reply is "I'm sorry, I can't find" followed by a blank where the key should be:</b> <b>KR - Single Issue</b> still filters on the deleted extractor's <code>issue_key</code>. It returns nothing within a few milliseconds, too fast to have searched, so <b>Issue Found?</b> takes ELSE. Re-point the filter condition to <b>Extract Keys (Code) / issue_key</b>.</li>
    <li><b>Nodes from another branch run too</b>, for example <b>Issue Keys Extractor</b>, <b>Iteration - Issues</b> and <b>LLM - Multiple Issues</b> on a single-issue question: one class handle connects to two branches, and Dify runs both. The answers can contradict each other. A "not found" reply can even appear with a REST-266 citation, because the other branch found it. Move the extra connection to the right class handle.</li>
  </ul>
</div>

Notice what the code does **not** do, and why:

- <code>PROJECTS</code> lists the prefixes that count as Jira keys. Without that list, a question about <code>UTF-8</code> would be read as issue number 8 in project UTF. Code only knows the patterns you give it, so pin them down.
- It doesn't guess. Anything that doesn't match returns an empty <code>issue_key</code>, and **Has Key?** sends the question to semantic search instead of a filter that can't match.
- The node also returns <code>issue_keys</code>, a list of every key in the question, so it can replace the **Issue Keys Extractor** in Steps 3 and 5 as well. A question without keys gives an empty list, and the **Has Issue Keys?** check in Step 5 works unchanged.

<div style={{ background: '#fffbe8', border: '2px solid #facc15', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0' }}>
  <b>Try it:</b> ask <code>Who is assigned to rest266?</code>, <code>Status of ticket #259</code> and <code>Does UTF-8 break JSON parsing?</code>, and compare the <b>Last Run</b> output of the code node with the LLM extractor's. For the best of both, run the code first and fall back to the LLM extractor only when the code finds nothing. You'll need an IF/ELSE and a Variable Aggregator to merge the two paths. The downloadable solution uses the LLM extractor, so you can compare the two.
</div>

### 2.2 IF/ELSE: Has Key?

Not every question routed here contains a key. *"Which issue reports that CORS preflight requests are not supported?"* asks about one issue, but describes it instead of naming it. The extractor then returns an empty <code>issue_key</code>. The exact-key filter can't match an empty key, so without this step the chatbot would answer "I can't find" for an issue that exists.

1. After the extractor, add an **IF/ELSE** node named **Has Key?**.
2. **IF:** **Issue Key Extractor / issue_key** **is not empty**. The **IF** branch continues to the exact-key retrieval in 2.3.
3. **ELSE:** connect it to **KR - General Project**, the semantic-search retriever you build in Step 4. A node can receive connections from several branches. If you haven't built Step 4 yet, come back and connect it then.

<Shot src={require('../static/img/dify/1.16.1/ex4/has-key.png').default} alt="Has Key? IF issue_key is not empty goes to KR - Single Issue; ELSE goes to KR - General Project" caption="No key → search by meaning instead of by key" width="420px" />

### 2.3 Knowledge Retrieval with a metadata filter: KR - Single Issue

1. From the **IF** handle of **Has Key?**, add a **Knowledge Retrieval** node and rename it **KR - Single Issue**. Keep **Query Text** as <code>sys.query</code>.
2. Click **+** next to **Knowledge** and add <code>{'Jira_API_Advanced_*'}</code>.
3. Set **Metadata Filtering** to **Manual** and click **Conditions** → **Add Condition**:
   - Field: <code>issue_key</code>
   - Operator: <b>is</b>
   - Value: switch to <b>Variable</b> and pick <b>Issue Key Extractor / issue_key</b>

<Shot src={require('../static/img/dify/1.16.1/ex4/kr-single-issue-filter.png').default} alt="Metadata Filter Conditions: issue_key is the Issue Key Extractor issue_key variable" caption="The exact-key filter" />

4. Open **Retrieval Setting**. Set **Top K** to <code>4</code> and leave **Score Threshold** **off**.

<div style={{ background: '#fef2f2', border: '2px solid #ef4444', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0' }}>
  <b>Why no score threshold here?</b> The filter already guarantees that only REST-266 can come back. A threshold would only drop it: with the question "What is REST-266 about?", REST-266 scores <b>0.27</b> in <code>{'Jira_API_Basic_*'}</code>. A 0.3 threshold removes it, and the chatbot then answers "can't find that issue" for an issue that exists. Use thresholds on open-ended searches (Exercise 3), not on exact-key lookups.
</div>

### 2.4 IF/ELSE: Issue Found?

If the key doesn't exist, the filtered retriever returns nothing. You might expect the LLM to say so. In testing, though, gpt-35-turbo-16k answered <code>What is REST-999 about?</code> with an invented issue, complete with status and assignee, even though the prompt said to refuse when the context is empty. Don't leave this decision to the model; make it with a rule.

1. After **KR - Single Issue**, add an **IF/ELSE** node named **Issue Found?**.
2. **IF:** **KR - Single Issue / result** **is not empty**. The **IF** branch continues to the LLM in 2.5.
3. **ELSE:** add an **Answer** node named **Answer - Issue Not Found**. Paste the text below, then replace <code>[issue_key]</code> with the variable **Issue Key Extractor / issue_key** (type <code>{'{'}</code> to pick it):

<Copy title="Answer - Issue Not Found → Answer">{`I'm sorry, I can't find [issue_key] in the project documentation. Check the issue key and try again.`}</Copy>

<Shot src={require('../static/img/dify/1.16.1/ex4/issue-found.png').default} alt="Issue Found? IF KR - Single Issue result is not empty goes to LLM - Specific Issue; ELSE goes to Answer - Issue Not Found" caption="An empty retrieval never reaches the LLM" width="420px" />

### 2.5 LLM and Answer

1. From the **IF** handle of **Issue Found?**, add an **LLM** node, rename it **LLM - Specific Issue**, select **gpt-35-turbo-16k**, and set **Temperature** to <code>0.3</code>.
2. Under **Context**, click **Set variable** and choose **KR - Single Issue / result**.
3. Paste this into the **SYSTEM** prompt:

<Copy title="LLM - Specific Issue → SYSTEM">{`You are a software testing assistant helping engineers understand Jira issues in the Atlassian REST project.

Answer only from the context below. Never use outside knowledge.
The context was filtered to the Jira issue the user asked about. If it is empty or does not mention that issue, reply exactly:
"I'm sorry, I can't find details about that issue in the project documentation."

Your reply should:
- Start with the issue key and its summary
- List the type, status and assignee
- Explain in two or three sentences what the issue changes or fixes
- End with "What to test": two to four concrete test ideas based on the description

Context:
{{#context#}}

User question:
{{#sys.query#}}`}</Copy>

<Shot src={require('../static/img/dify/1.16.1/ex4/llm-specific-issue.png').default} alt="LLM - Specific Issue with Context set to KR - Single Issue result and the pasted SYSTEM prompt" caption="Context bound to the filtered retriever; the pasted prompt shows the Context block and the query variable" width="420px" />

4. Add an **Answer** node, rename it **Answer - Specific Issue**, and set its content to **LLM - Specific Issue / text** (type <code>{'{'}</code> or use the <b>{'{'}x{'}'}</b> button).

### ✅ Check it

## 🛠️ Step 3: Branch `list_issues`: One Retrieval per Issue

One search for "REST-266 and REST-265" returns whichever chunks score best, often mostly one issue. This branch extracts **every** key and runs one filtered retrieval per key with an **Iteration**. A **Code** node then combines the results and reports any keys that weren't found.

<div style={{ background: '#f8fafc', border: '1px solid #cbd5e1', borderRadius: '8px', padding: '0.6em 1.2em', margin: '1em 0', fontFamily: 'monospace' }}>
  list_issues → Issue Keys Extractor → Iteration - Issues [ KR - Each Issue ] → Combine Results → LLM - Multiple Issues → Answer - Multiple Issues
</div>

### 3.1 Parameter Extractor: Issue Keys Extractor

From the <code>list_issues</code> handle, add a **Parameter Extractor** named **Issue Keys Extractor** (gpt-35-turbo-16k, Temperature <code>0</code>) with one parameter:

- **Name:** <code>issue_keys</code> (plural; the Iteration reads this exact name)
- **Type:** Array[String]
- **Required:** on
- **Description:** <code>Every Jira issue key in the question, for example ["REST-266", "REST-265"].</code>

<Copy title="Issue Keys Extractor → Instruction">{`Extract every Jira issue key mentioned in the user's question, in the order they appear.
A Jira issue key is an uppercase project prefix, a hyphen and a number, for example REST-266.
Normalize other spellings to that format. This project's prefix is REST, so "rest 266", "REST266", "issue 266" and "ticket 266" all become REST-266.
If the question contains no issue key, return an empty list.`}</Copy>

### 3.2 Iteration: Iteration - Issues

1. After the extractor, add an **Iteration** node named **Iteration - Issues**.
2. **Input:** **Issue Keys Extractor / issue_keys**. The Iteration runs its inner nodes once per key, and the current key is available as <code>item</code>.
3. Inside the Iteration box, click **+** after the start icon and add a **Knowledge Retrieval** named **KR - Each Issue**:
   - **Query Text:** **Iteration - Issues / item** (not <code>sys.query</code>, which contains every key)
   - **Knowledge:** <code>{'Jira_API_Advanced_*'}</code>
   - **Metadata Filtering:** Manual, <code>issue_key</code> **is** Variable **Iteration - Issues / item**
   - **Retrieval Setting:** Top K <code>4</code>, Score Threshold off

<Shot src={require('../static/img/dify/1.16.1/ex4/kr-each-issue.png').default} alt="KR - Each Issue: Query Text is the Iteration item and the issue_key filter uses the same item" caption="Inside the loop, the query and the filter both use the current item" />

4. Back on the Iteration node, set:
   - **Output Variables:** **KR - Each Issue / result**
   - **Parallel Mode:** on (optional; issues are retrieved at the same time)
   - **Error Response Method:** **Remove Abnormal Output**, so one failing key doesn't fail the whole run
   - **Flatten Output:** off

<Shot src={require('../static/img/dify/1.16.1/ex4/iteration-settings.png').default} alt="Iteration - Issues settings: input issue_keys, output KR - Each Issue result, Remove Abnormal Output" caption="Input, output and error handling" width="420px" />

### 3.3 Code: Combine Results

The Iteration returns a list of results, one per key. A key that doesn't exist, such as REST-999, just produces an empty result, and nothing tells the LLM that it's missing. This Code node flattens the results into one context list and compares the requested keys with the keys actually found.

1. After the Iteration, add a **Code** node named **Combine Results**. Keep **Python3**.
2. **Input Variables:** the names must match the arguments of <code>main()</code> in the code below:
   - rename <code>arg1</code> to <code>inputs</code> and pick **Iteration - Issues / output**

### When something doesn't pass

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| A made-up answer for a key that doesn't exist | The LLM runs on an empty context | Add the **Issue Found?** IF/ELSE from Step 2.4 |
| "I'm sorry, I can't find  in the project documentation" (a blank where the key should be) | The question names no key, and there is no fallback | Add the **Has Key?** IF/ELSE from Step 2.2 |
| "Can't find" for an issue that exists | Score Threshold is on in the filtered retriever, or the filter points at the wrong or a deleted variable | Turn the threshold off. Open the filter's **Conditions** and check that the value is the current extractor's <code>issue_key</code> (or the Iteration's <code>item</code>) |
| Nodes from two branches run for one question, and the answers are mixed | One class handle connects to two branches | Keep one connection per class handle; move the extra one to the right class |
| "issue 266" becomes <code>ISSUE-266</code> | The extractor instruction lacks the normalization rule | Paste the extractor instruction from this page |
| Every project or testing question gets "can't find relevant information" | The LLM's Context field is empty | Set Context to the branch retriever's <code>result</code> |
| The Iteration runs zero times | The extractor output name doesn't match (<code>issue_key</code> vs <code>issue_keys</code>) | Use <code>issue_keys</code> (Array[String]) and re-select the Iteration input |
| A multi-issue answer only describes one issue, or mixes them up | The inner retriever searches with <code>sys.query</code> | Use <b>Iteration / item</b> as Query Text and as the filter value |
| The question goes down the wrong branch | Classifier temperature is too high or the instruction is missing | Temperature <code>0</code>, and paste the classifier instruction |

Open the **Workflow Process** of a run (the label above the answer) or the node's **Last Run** tab to see each node's input and output, just like the retrieval trace in Exercise 3.

## 🔭 Going Further

You now use two advanced RAG techniques: **metadata filtering** (exact-key retrieval) and **multi-query retrieval** (one search per issue). Here are more ideas to try on your own.
