### 🎛️ Step 3: Try It — Tune the LLM

Now that the workflow runs, see how the model's parameters change its answers. Open the <b>LLM</b> node and click the model name to open its parameter settings:

<ul>
  <li><b>Temperature</b>: how much randomness the model uses. Low values (<code>0.2-0.4</code>) give consistent, repeatable answers, which is what you want for testing tasks. Higher values give more varied, creative answers.</li>
  <li><b>Top P</b>: another way to limit randomness. Keep it at <code>0.8-1.0</code> and don't change it together with Temperature.</li>
  <li><b>Max Tokens</b>: caps the answer length. This keeps cost down and cuts rambling answers.</li>
</ul>

<Explore title="See what Temperature does to the probabilities" href="https://poloclub.github.io/transformer-explainer/" source="Transformer Explainer">

  <p><b>What to look for:</b> pick a sentence from the <b>Examples</b> menu and watch the probability bars. Drag Temperature all the way down: the top word takes almost all the probability, so the model picks the same word every time. Drag it up: the bars even out and less likely words get picked more often. That's why low temperature gives repeatable answers and high temperature gives varied ones, which you're about to see in Dify.</p>
  <p style={{ margin: 0 }}><b>Heads-up:</b> the Examples work straight away. Typing your own sentence downloads the 600 MB model first, so save that for a good connection.</p>

## 🅱️ Path B: Your own self-hosted model (optional)

Use this when you are studying on your own, or when the classroom model is unavailable and you would rather not use Azure.

<ul>
  <li><b>Ollama on the same host or network as Dify</b>: install Ollama, run <code>ollama pull qwen2.5:1.5b</code>, and use the Ollama provider's native endpoint.</li>
  <li><b>Ollama on your laptop with remote Dify</b>: do not enter <code>localhost</code>. Dify resolves that name inside its own container, not on your machine. Use an authenticated HTTPS gateway or a private network route Dify can reach.</li>
  <li><b>LM Studio</b>: start its local server mode and use its documented OpenAI-compatible endpoint, only when Dify can reach it.</li>
  <li><b>Self-hosted vLLM/TGI</b>: expose a private, authenticated endpoint reachable from the Dify runtime network.</li>
</ul>

**Never expose Ollama's unauthenticated port to the internet.** It has no authentication of its own, and its API can pull and delete models. Put TLS and authentication in front of it, and use the smallest model and context window that meet the goal.

## 🚦 When the classroom model is busy or down

The shared host serves the whole room, so you will occasionally meet its limits. These are expected and each has a specific meaning.

| What you see | What it means | What to do |
|---|---|---|
| `429` / "at capacity" | Too many people generating at once. Requests queue; past the queue limit they are refused. | Wait a few seconds and retry. Do not retry in a tight loop — it makes the queue worse for everyone. |
| `401` | Your token is wrong, expired, or was revoked. | Re-copy it from the assignment page. If it still fails, ask your instructor. |
| Very slow first response | The model was evicted from memory and is reloading, or the host is saturated. | Wait. The first request after an idle period legitimately takes much longer. |
| `502` / `503` / connection refused | The service is down or restarting. | **Switch your LLM node back to Azure and carry on.** |

### 🧯 Troubleshooting

<ul>
  <li><b>Empty answer, but the run shows SUCCESS</b> (output <code>"text": ""</code>, about 1 completion token, well under a second): your LLM node only has a SYSTEM message. Local chat models such as Llama 3.2 answer a <b>USER</b> turn; with only a system message they end their turn straight away. Click <b>+ Add Message</b>, choose <b>USER</b>, insert <code>query</code> there, remove <code>query</code> from the system prompt, and run again. Azure hides this mistake, so the same prompt can work on Azure and fail locally.</li>
  <li><b>401 Unauthorized</b>: re-copy the token from your assignment page — a trailing space is the usual cause. If it still fails, the token was revoked; ask your instructor.</li>
  <li><b>429 / "at capacity"</b>: the shared host is saturated. Wait and retry once; do not loop.</li>
  <li><b>Connection failed</b>: confirm the base URL matches your card exactly, including <code>https://</code> and with no trailing path. On Path B, <code>localhost</code> means the Dify runtime, not your laptop.</li>
  <li><b>Model not listed</b>: the model name must match the tag exactly, including the part after the colon.</li>
  <li><b>Slow answers</b>: expected on a shared CPU host. Reduce max tokens and keep retrieval chunk count small while tuning.</li>
  <li><b>Poor relevance</b>: keep your embedding model quality high even when generation uses a smaller local model. Retrieval quality and generation quality are separate problems.</li>
  <li><b>Timeouts in Dify</b>: raise the node timeout to 60-120s. CPU inference is genuinely slow, and a short timeout is indistinguishable from a broken model.</li>
</ul>
