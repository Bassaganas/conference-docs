## 🧠 How Do You Test a RAG?

A RAG answer can go wrong in two different places, so we test them separately:

| Layer | The question a test asks | Example check |
|---|---|---|
| **Retrieval** | Did the search find the right chunk? | REST-266 is ranked 1st for a question about unknown JSON properties |
| **Generation** | Is the answer correct and based **only** on what was found? | The answer mentions REST-266, cites it, and mentions no issue it didn't retrieve |
| **Behaviour** | Does it say "I don't know" when it should? | "Why is the sky blue?" gets a polite refusal |
| **Speed** | Is it fast enough? | The answer arrives in under 30 seconds |

There are three kinds of checks, from cheapest to most powerful:

1. **Deterministic** – "contains", regex, "the right document is cited", latency. Free and repeatable. This is where you start.
2. **Semantic similarity** – "means the same as" an expected answer, using embeddings.
3. **LLM-as-a-judge** – a second LLM grades the answer against a written criterion (for example: *is every claim supported by the retrieved chunks?*). Powerful, but it costs tokens and can itself be wrong.

All tests are driven by a **golden dataset**: a list of *question + fact the answer must contain + document that must be the source*.

<div style={{ background: '#e0f2fe', border: '2px solid #38bdf8', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  💡 <b>Why write tests at all?</b> Dify gives you <b>Retrieval Testing</b> in the knowledge base, <b>Logs</b> with user feedback, and tracing integrations (Langfuse, LangSmith, Opik, Phoenix…). All of them are great for looking at one answer. None of them re-runs a set of questions after every change and tells you what broke. That is what an automated regression suite does.
</div>

Our tests are written in a Given / When / Then style, so they read like a specification:

```gherkin
Scenario: Grounded answer cites the right Jira issue
  Given the chatbot is connected to the Jira knowledge base
  When I ask "Which issue is about the default Jackson configuration erroring out on unknown properties?"
  Then the answer mentions "REST-266"
  And the answer cites the document for REST-266
  And it only mentions Jira issues that it actually retrieved
  And it answers within 30 seconds
```

## 🛠️ Step 3: Level 1 – Test Retrieval

Retrieval tests search your knowledge base directly. **No LLM is involved**, so they are fast, free and give the same result every time. They use the same settings as the Exercise 2.1 benchmark (hybrid search, weights 0.3 / 0.7, Top K 10, threshold 0.05).

```bash
npm run test:retrieval
```

Expected result – 3 passed:

```text
✓ Level 1 – Knowledge retrieval › exact issue wording finds REST-266 first
✓ Level 1 – Knowledge retrieval › natural question finds REST-266 first
✓ Level 1 – Knowledge retrieval › unrelated question returns no chunks
```

<div style={{ background: '#e0f2fe', border: '2px solid #38bdf8', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  💡 If a retrieval test fails, the chatbot cannot give a grounded answer either. Always look at retrieval first. Try adding a vague question such as <i>"Which Jira work has important test implications for REST API compatibility?"</i> to the <code>retrieval</code> list: depending on how your knowledge base was ingested, REST-266 may not even be in the top 10. Vague questions are where retrieval is weakest.
</div>

## 🛠️ Step 4: Level 2 – Test the Chatbot End to End

Now we ask your published chatbot real questions. LLM wording changes from run to run, so we **never compare exact text**. We check properties of the answer instead:

| Scenario | What the test checks |
|---|---|
| Grounded answers (5 questions) | Mentions the right fact, cites the right document, mentions no issue it didn't retrieve, answers in under 30 s |
| Out-of-scope question | "Why is the sky blue?" → a refusal and **no** citations |
| Unknown issue | "Summarize REST-999" → says it can't find it and invents nothing |
| Error path | A wrong API key → `401` with a clear error body |

```bash
npm run test:chatbot
npm run report    # opens the HTML report
```

Expected result – **8 passed**. Open the report (Codespaces offers to open port 9323) and click a test: every Given / When / Then step is listed, together with the chatbot's actual answer and its token usage.

  <b>Add your own test – no code needed.</b> Open <code>golden/jira-rest.json</code>, copy one entry of the <code>grounded</code> list and change the question, the fact and the expected issue. ## 🛠️ Step 5: Break It on Purpose

A test is only useful if it fails when something breaks. Make **one** change at a time in your Chatflow, **publish**, and run `npm test`. Before you run, predict which tests will fail.

| Sabotage | Where |
|---|---|
| Raise the score threshold to **0.9** | Knowledge Retrieval node → retrieval settings |
| Remove the knowledge context from the prompt | LLM node → Context |
| Replace the system prompt with *"Answer from your general knowledge."* | LLM node → System prompt |

Which level failed – retrieval or chatbot? Did the failure message tell you **what** went wrong? When you're done, restore your last good version from the **version history** (Exercise 3) and publish again. All tests should be green again.

<div style={{ background: '#e0f2fe', border: '2px solid #38bdf8', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  💡 Level 1 calls the knowledge base with its own fixed settings, so it only notices problems in the <b>data</b>, not in the app's retrieval node. Level 2 tests what your users actually get.
</div>

## 🔎 Step 6: Investigate a Real Finding

Exercise 3 uses this acceptance question:

> *Which issue creates a backward-compatibility risk when unknown JSON properties are accepted?*

The expected answer is **REST-266**. Add it to the `grounded` list in `golden/jira-rest.json`:

```json
{
  "name": "exercise 3 acceptance question",
  "query": "Which issue creates a backward-compatibility risk when unknown JSON properties are accepted?",
  "mustMention": ["REST-266"],
  "expectedIssue": "REST-266"
}
```

Run it a few times (please don't go higher than 3 – the whole class shares the same LLM quota):

```bash
npx playwright test -g "acceptance" --retries=0 --repeat-each=3
```

When we prepared this workshop, the chatbot often answered **REST-430** (another Jackson issue that mentions "backwards incompatible"), and sometimes also mentioned **REST-402** – an issue that is not in the knowledge base, but is referenced inside the text of REST-430. Look at the failure details and answer:

- Was REST-266 **cited**? (Check the "cites the document" step.) If it was, retrieval did its job and the mistake happened in **generation**.
- REST-402 is not one of the 23 issues. Is mentioning it a hallucination? (Hint: search the cited chunks for "REST-402" – the "only mentions Jira issues that it actually retrieved" step does exactly that.)
- Why does the same question sometimes pass and sometimes fail? What does that mean for how many times you should run LLM tests?
- What would you change to fix it: the prompt, the model, or the retrieval settings? Try it and re-run.

## ⚖️ Step 7: Level 3 – LLM-as-a-Judge

Levels 1 and 2 can check *that* REST-266 is mentioned. They cannot check whether **every sentence** of an answer is backed by the documents, or whether a refusal quietly explains the physics of the sky anyway. For that we use a second LLM as a **judge**: it receives the question, the answer, the retrieved chunks (and, when we have one, a reference answer) and grades **one criterion** with PASS or FAIL.

### Why this works – and where it doesn't

The technique was popularised by Zheng et al. (2023), who found that a strong LLM judge agreed with human preferences **over 80%** of the time – about as often as two humans agree with each other. The same paper names the judge's weaknesses: it favours the first answer it sees (**position bias**), longer answers (**verbosity bias**) and answers written by itself (**self-enhancement bias**), and it can be misled by the very answer it is grading.

For RAG, the most useful criterion is **faithfulness** (Es et al., 2024 – the RAGAS paper): split the answer into individual claims and check each claim against the retrieved context. An answer can be *faithful but wrong* (it correctly repeats a wrong chunk) or *correct but unfaithful* (right from the model's memory, not from your documents). That's why we test faithfulness and correctness separately.

Our judge follows the practices that research and practitioners agree on:

| Practice | In our judge | Source |
|---|---|---|
| **One criterion per judge call** | Separate criteria for faithfulness, correctness and refusal | Evidently; Anthropic |
| **Binary verdict** instead of a 1–10 score | `PASS` or `FAIL` – easy to act on, easy to measure | Husain; Yan |
| **Reasoning before the verdict** | The judge writes 1–3 sentences, then decides | Liu et al. (G-Eval) |
| **Give the judge the evidence** | Retrieved chunks for faithfulness, a reference answer for correctness | Es et al. (RAGAS); Zheng et al. |
| **Structured output, temperature 0** | JSON reply, temperature 0 | Evidently |
| **A safe answer when unsure** | "If you are unsure, FAIL" in the judge prompt | Anthropic |
| **Validate the judge before trusting it** | Level 3A: answers whose correct verdict we already know | Shankar et al.; Husain |

<div style={{ background: '#fffbe8', border: '2px solid #facc15', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  <b>Who validates the validator?</b> A judge is just another LLM prompt – it can be lenient, biased or plain wrong (Thakur et al., 2024; Shankar et al., 2024). So we test the judge <b>first</b>: in Level 3A we feed it answers where <i>we</i> know the right verdict (a faithful summary must PASS, an answer with an invented assignee must FAIL). Only when the judge gets those right do we let it grade the chatbot in Level 3B.
</div>

### 7.2 Level 3A – Calibrate the judge

```bash
npm run test:judge -- -g "Calibrate"
```

Expected result – **6 passed**: three answers that must PASS and three that must FAIL (an invented assignee, a wrong reporter, a refusal that explains Rayleigh scattering anyway). Open the report: every test shows the judge's **reasoning**. If the judge gets a calibration case wrong, don't use it to grade your chatbot yet – improve the criterion wording in `golden/jira-rest.json` or switch the judge to a stronger model, then re-run.

```bash
npm run test:judge -- -g "Judge the chatbot"
```

Expected result – **4 passed**: two faithfulness checks, one correctness check against a reference answer, and one refusal check. ## 🧯 Troubleshooting

| Symptom | Fix |
|---|---|
| Tests are **skipped** | A value in `.env` is missing or still a placeholder |
| `401 unauthorized` | Wrong key type: the chatbot and the judge need their own `app-…` key, retrieval needs the `dataset-…` key |
| `400 Workflow not published` | Click **Publish** in your Chatflow or judge workflow |
| `404` on retrieve | `DIFY_DATASET_ID` is wrong – copy it from the knowledge base URL |
| "cites the document" fails with *cited: nothing* | In the LLM node, **Context** must be set to the Knowledge Retrieval result, and **Citations and Attributions** must be enabled |
| Retrieval tests fail | Check that all 23 documents show **Available** in your knowledge base |
| Tests are slow or fail with a rate-limit error | The class shares one LLM quota. The tests already wait and retry; wait a minute and run again |
| `Judge workflow failed` | Open the judge in Dify → **Logs** and check the Judge node's model is configured |
| Judge says *Could not read the judge's reply as JSON* | The model ignored the output format – try a stronger judge model |
