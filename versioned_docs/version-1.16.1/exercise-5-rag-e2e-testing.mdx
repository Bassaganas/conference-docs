## 🧠 How Do You Test a RAG?

A RAG answer can go wrong in two different places, so we test them separately:

| Layer | The question a test asks | Example check |
|---|---|---|
| **Retrieval** | Did the search find the right chunk? | REST-266 is ranked 1st for a question about unknown JSON properties |
| **Generation** | Is the answer correct and based **only** on what was found? | The answer mentions REST-266, cites it, and mentions no issue it didn't retrieve |
| **Behaviour** | Does it say "I don't know" when it should? | "Why is the sky blue?" gets the polite fallback reply |
| **Speed** | Is it fast enough? | The answer arrives in under 30 seconds |

There are three kinds of checks, from cheapest to most powerful:

1. **Deterministic** – "contains", regex, "the right document is cited", latency. Free and repeatable. This is where you start.
2. **Semantic similarity** – "means the same as" an expected answer, using embeddings.
3. **LLM-as-judge** – a second LLM grades the answer (for example: *is it faithful to the retrieved chunks?*). Powerful, but it costs tokens and can itself be wrong.

All tests are driven by a **golden dataset**: a list of *question + fact the answer must contain + document that must be the source*.

<div style={{ background: '#e0f2fe', border: '2px solid #38bdf8', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  💡 <b>Why write tests at all?</b> Dify gives you <b>Retrieval Testing</b> in the knowledge base, <b>Logs</b> with user feedback, and tracing integrations (Langfuse, LangSmith, Opik, Phoenix…). All of them are great for looking at one answer. None of them re-runs a set of questions after every change and tells you what broke. That is what an automated regression suite does.
</div>

Our tests are written in a Given / When / Then style, so they read like a specification:

```gherkin
Scenario: Grounded answer cites the right Jira issue
  Given the chatbot is connected to the Jira knowledge base
  When I ask "Which issue is about the default Jackson configuration erroring out on unknown properties?"
  Then the answer mentions "REST-266"
  And the answer cites the document for REST-266
  And it only mentions Jira issues that it actually retrieved
  And it answers within 30 seconds
```

## 🛠️ Step 3: Level 1 – Test Retrieval

Retrieval tests search your knowledge base directly. **No LLM is involved**, so they are fast, free and give the same result every time. They use the same settings as the Exercise 2.1 benchmark (hybrid search, weights 0.3 / 0.7, Top K 10, threshold 0.05).

```bash
npm run test:retrieval
```

Expected result – 4 passed:

```text
✓ Level 1 – Knowledge retrieval › exact issue wording finds REST-266 first
✓ Level 1 – Knowledge retrieval › natural question finds REST-266 first
✓ Level 1 – Knowledge retrieval › vague question still finds REST-266 in the top 3
✓ Level 1 – Knowledge retrieval › unrelated question returns no chunks
```

<div style={{ background: '#e0f2fe', border: '2px solid #38bdf8', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  💡 If a retrieval test fails, the chatbot cannot give a grounded answer either. Always look at retrieval first.
</div>

## 🛠️ Step 4: Level 2 – Test the Chatbot End to End

Now we ask your published chatbot real questions. LLM wording changes from run to run, so we **never compare exact text**. We check properties of the answer instead:

| Scenario | What the test checks |
|---|---|
| Grounded answers (5 questions) | Mentions the right fact, cites the right document, mentions no issue it didn't retrieve, answers in under 30 s |
| Out-of-scope question | "Why is the sky blue?" → polite fallback and **no** citations |
| Unknown issue | "Summarize REST-999" → says it can't find it and invents nothing |
| Error path | A wrong API key → `401` with a clear error body |

```bash
npm test          # runs Level 1 + Level 2
npm run report    # opens the HTML report
```

Expected result – **12 passed**. Open the report (Codespaces offers to open port 9323) and click a test: every Given / When / Then step is listed, together with the chatbot's actual answer and its token usage.

<div style={{ background: '#fffbe8', border: '2px solid #facc15', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  <b>Add your own test – no code needed.</b> Open <code>golden/jira-rest.json</code>, copy one entry of the <code>grounded</code> list and change the question, the fact and the expected issue. For example: <i>"Which issue reports that the WADL is invalid?"</i> must mention <code>REST-404</code>. Run <code>npm run test:chatbot</code> again.

## 🛠️ Step 5: Break It on Purpose

A test is only useful if it fails when something breaks. Make **one** change at a time in your Chatflow, **publish**, and run `npm test`. Before you run, predict which tests will fail.

| Sabotage | Where |
|---|---|
| Raise the score threshold to **0.9** | Knowledge Retrieval node → retrieval settings |
| Remove the knowledge context from the prompt | LLM node → Context |
| Replace the system prompt with *"Answer from your general knowledge."* | LLM node → System prompt |

Which level failed – retrieval or chatbot? Did the failure message tell you **what** went wrong? When you're done, restore your last good version from the **version history** (Exercise 3) and publish again. All tests should be green again.

<div style={{ background: '#e0f2fe', border: '2px solid #38bdf8', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  💡 Level 1 calls the knowledge base with its own fixed settings, so it only notices problems in the <b>data</b>, not in the app's retrieval node. Level 2 tests what your users actually get.
</div>

## 🔎 Step 6: Investigate a Real Finding

Exercise 3 uses this acceptance question:

> *Which issue creates a backward-compatibility risk when unknown JSON properties are accepted?*

The expected answer is **REST-266**. Add it to the `grounded` list in `golden/jira-rest.json`:

```json
{
  "name": "exercise 3 acceptance question",
  "query": "Which issue creates a backward-compatibility risk when unknown JSON properties are accepted?",
  "mustMention": ["REST-266"],
  "expectedIssue": "REST-266"
}
```

Run it several times:

```bash
npx playwright test -g "acceptance" --retries=0 --repeat-each=5
```

When we prepared this workshop, the chatbot often answered **REST-430** (another Jackson issue that mentions "backwards incompatible"), and sometimes even mentioned an issue that **does not exist** in the dataset. Look at the failure details and answer:

- Was REST-266 **cited**? (Check the second step of the failed test.) If it was, retrieval did its job and the mistake happened in **generation**.
- Did the "only mentions Jira issues that it actually retrieved" step catch an invented issue?
- Why does the same question sometimes pass and sometimes fail? What does that mean for how many times you should run LLM tests?
- What would you change to fix it: the prompt, the model, or the retrieval settings? Try it and re-run.

## 🌟 Bonus: Level 3 – LLM-as-Judge

Some qualities can't be checked with "contains". Is the answer **faithful** to the chunks that were retrieved? Is the refusal polite and free of invented facts? Here a second LLM grades your chatbot, using <a href="https://www.promptfoo.dev/" target="_blank" rel="noopener noreferrer">promptfoo</a>.

1. From the portal's **Azure LLM** card, add the judge settings to `.env`:

   ```bash
   AZURE_API_KEY=...
   AZURE_API_HOST=<your-resource>.openai.azure.com
   AZURE_DEPLOYMENT=<deployment name>
   ```

2. Run the evaluation and open the results table (port 15500):

   ```bash
   npm run test:judge
   npm run judge:view
   ```

3. Open `promptfooconfig.yaml`. Find the `context-faithfulness` check (the judge compares the answer with the chunks Dify returned in `retriever_resources`) and the `llm-rubric` checks (plain-English grading rules). Write one rubric of your own.

<div style={{ background: '#fffbe8', border: '2px solid #facc15', borderRadius: '8px', padding: '0.8em 1.2em', margin: '1em 0 2em 0' }}>
  <b>Judges can be wrong too.</b> Read the judge's reasons in the results table. Do you agree with every verdict? Deterministic checks first, judges for what they can't cover.
</div>

## 🧯 Troubleshooting

| Symptom | Fix |
|---|---|
| Tests are **skipped** | A value in `.env` is missing or still a placeholder |
| `401 unauthorized` | Wrong key type: the chatbot needs the `app-…` key, retrieval needs the `dataset-…` key |
| `400 Workflow not published` | Click **Publish** in your Chatflow |
| `404` on retrieve | `DIFY_DATASET_ID` is wrong – copy it from the knowledge base URL |
| "cites the document" fails with *cited: nothing* | In the LLM node, **Context** must be set to the Knowledge Retrieval result, and **Citations and Attributions** must be enabled |
| Retrieval tests fail | Check that all 23 documents show **Available** in your knowledge base |
| `429` | Too many requests at once – wait a minute and run again |
| Level 3: `API call error … azure` | Check the three `AZURE_*` values; the host has no `https://` and no path |
